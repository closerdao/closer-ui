# Quests UI — notes for the backend

What the `closer-ui` quests feature sends, expects back, and still needs. Written
against the Quest API reference (models `quests`, `questEntries`, `questActions`).

## Pages shipped

| Route | Who sees it | What it calls |
| --- | --- | --- |
| `/quests` | everyone | `GET /quest` |
| `/quests/:slug` | everyone | `GET /quest/:slug`, `GET /quest/:slug/me`, `GET /quest/:slug/leaderboard`, `GET /questaction`, `POST …/action` |
| `/quests/create` | quest admins | `POST /Quest` |
| `/quests/:slug/edit` | quest admins | `GET /quest/:slug`, `PATCH /quest/:slug`, `DELETE /Quest/:id` |
| `/quests/:slug/audit` | everyone, once locked | `GET /quest/:slug/audit` |

The quest page also carries the admin close-out panel, which calls
`GET /questaction?where={"questId","status":"pending"}`,
`POST …/action/:actionId/verify`, `POST …/lock`, `POST …/draw` and
`POST …/settle`.

Admin access is gated client-side on a new RBAC page key **`QuestCreation`**,
granted to `admin`, `steward` and `community-curator` — matching
`Quest.adminRoles`. The server is still the authority; the UI only hides
controls.

## Visibility split

Guests and members see **live**, **locked** and **settled** quests only. The list
page server-renders exactly that filter:

```
GET /quest?where={"status":{"$in":["live","locked","settled"]}}&limit=50&sort_by=-start
```

Admins additionally fetch, client-side and authenticated:

```
GET /quest?where={"status":{"$in":["scheduled","draft"]}}&limit=50&sort_by=-start
```

**Ask:** please enforce this server-side too. Right now nothing stops an
unauthenticated `GET /quest?where={"status":"draft"}` from returning drafts.
Drafts and scheduled quests should be readable only by `Quest.adminRoles`.

## Editor conformance with the integrity rules

The form now mirrors the rules the model enforces, so an admin hits them in the
browser rather than as a 4xx:

- **Status** only offers the legal next steps (`draft → scheduled → live`, or
  aside to `cancelled`). `locked` and `settled` are never offered — they are
  reached through the routes.
- **Award currency** is a dropdown built from the platform's config — carrots,
  the booking token, the fiat currency — not free text.
- **Token prizes** are rejected client-side on a quest whose category is not
  `tokenGrowth`.
- **Ranked prizes** are always written contiguously from `"1"`, and the form
  blocks a save with more ranks than `winnerCount`.
- `eligibility.minAccountAgeDays` and `eligibility.requiresVerifiedEmail` are
  editable; `excludeUserIds` is not exposed yet.
- `raffleConfig.drawMethod` is editable, and choosing `externalSeed` makes the
  admin panel require a seed at draw time.

## Create / edit payloads

Create posts the full terms; edit sends the same shape, except once a quest is
past `draft`/`scheduled` the UI sends **only** `title`, `slug`,
`shortDescription`, `description`, `visual` and `status`, because everything else
is frozen server-side. The form disables those inputs and explains why.

```jsonc
{
  "title": "The Citizen Raffle",
  "slug": "citizen-raffle",            // omitted when blank, so you generate it
  "shortDescription": "…",
  "description": "…",
  "category": "tokenGrowth",
  "type": "raffle",
  "status": "draft",
  "visual": { "emoji": "🐑", "coverImage": "https://…" },
  "start": "2026-09-01T08:00:00.000Z",  // UTC
  "end":   "2026-09-08T22:59:00.000Z",  // UTC, exclusive
  "timezone": "Europe/Lisbon",          // display only
  "roleRequired": ["citizen"],
  "prize": {
    "ranked": { "1": { "kind": "perk", "title": "Free treehouse upgrade" } },
    "eachAction": { "kind": "currency", "cur": "carrots", "val": 1 },
    "notes": "…"
  },
  "raffleConfig": { /* see below */ }
}
```

`prize` is omitted entirely when no award is configured, rather than sent as `{}`.

### Ticket source keys are generated by the UI

Admins never type a `key`. The form asks for a **label** and mints the key from
it (`"$TDF bought during the quest"` → `tdf_bought_during_the_quest`),
deduplicating with `_2`, `_3`. An existing source keeps whatever key it already
has, so `ticketsBySource` and issued tickets stay aligned when a label is
renamed.

**Ask:** if you ever generate or rewrite keys server-side, keep them stable
across updates for the same reason.

### Trigger events are a closed list

The trigger dropdown offers only the source types the backend aggregates:

| Value | Shown as | Filters the UI sets |
| --- | --- | --- |
| `booking.confirmed` | Event booked | `{ eventId }`, required — admin picks from `GET /event?where={"end":{"$gt":now}}` |
| `stay.completed` | Stay completed | `{ eventId?, fullDuration? }`, both optional and omitted when unset |
| `token.purchased` | Token purchased | `{ token: <web3.bookingToken>, withinQuestWindow: true }` |
| `custom` | — never offered | `{}` — set automatically, see below |

`custom` is not in the dropdown on purpose. It follows from the source's
**verification** instead: choosing *Admin review* writes
`trigger: { event: 'custom', filter: {} }`, since that is the only trigger
`POST …/action` accepts and the only way a source can take member-submitted
proof. Tying the two together means an admin cannot build the broken
combination — an admin-reviewed source with an automatic trigger, or a `custom`
source nothing can submit against.

**Ask:** if you add or rename a source type, tell us — the list lives
in `packages/closer/constants/quests.constants.ts` and has to be updated by hand.
A `GET /quest/event-types` endpoint returning `{ value, requires, accepts }`
would let the UI stop hard-coding it.

## Nobody joins or leaves a quest

Entry is automatic and not negotiable. **The UI never calls `POST …/join` or
`POST …/withdraw`** — there are no wrappers for them in `quests.api.ts` at all.
A member who qualifies is in; the entry panel says so outright, naming
`roleRequired` when the quest is gated, rather than sitting there looking like it
is waiting on them.

Two consequences worth holding on the backend:

- `…/me` must return a usable view for a qualifying member with **no entry row
  yet** — zeroed counts rather than a 404 — because nothing creates that row up
  front any more.
- `…/action` must keep auto-joining whoever submits one, which it already
  documents. That is now the only path that creates an entry from the UI.

`entry.status === 'withdrawn'` is still rendered as a read-only notice, since the
API can report it and a member should not silently accrue tickets that do not
count. Nothing in the UI can cause or undo that state.

**Ask:** if withdrawal is genuinely dead, tell us and we will drop the notice
too — and you can retire the route.

## Taking a quest live

`status` only moves one step at a time, so publishing a draft is two sequential
`PATCH`es (`draft → scheduled`, then `scheduled → live`). `publishQuest` walks
that path; admins see one **Take it live** button on the draft card and in the
close-out panel. There is no way back — the UI says so, since the only sideways
move the model allows is `cancelled`.

**Ask:** if you would rather we did not fire two PATCHes in a row, a
`POST /quest/:slug/publish` that does the walk server-side would be cleaner.

## Ticket sources link to where the ticket is earned

The entry panel turns each source's trigger back into somewhere a member can
actually go: `booking.confirmed` → the event's page (resolved from
`filter.eventId` via `GET /event/:id`), `stay.completed` → `/stay`,
`token.purchased` → `/token`. Sources verified by hand get no link — those are
submitted on the quest page itself.

**Ask:** `filter.eventId` costs us one `GET /event/:id` per source. Returning a
resolved `{ slug, name }` alongside the quest would remove that round trip.

## The leaderboard is pulled, not pushed

Tickets are aggregated backend-side from bookings, stays and token purchases
rather than from anything the member does on the page, so someone sitting on an
open quest would otherwise watch a frozen scoreboard. `useQuestLiveData` re-pulls `…/me`, `…/leaderboard`
and the caller's actions **every 30s while the quest is open**, pausing while the
tab is hidden and catching up on focus. Closed quests fetch once and stop.

That is roughly one request per member per 30s per open quest page.
**Ask:** if that is too much for `…/leaderboard`, say so and we will lengthen the
interval — or better, cache the leaderboard response server-side for ~15s, since
every viewer of a quest asks for exactly the same rows.

## Stale reads were the biggest bug we hit

The shared axios client caches client-side GETs for five minutes, which quietly
broke three things: the leaderboard "poll" re-read its own cache, an admin who
locked or drew saw the quest sit unchanged, and an edit landed back on a stale
detail page. Now: `…/me`, `…/leaderboard` and the action/entry reads always pass
`cache: false`, every quest write calls `invalidateGetCache('/quest')`, and the
detail page holds the quest in state and refetches it after each admin action.

Worth knowing if you add endpoints here — a new read that moves during a quest
needs the same treatment.

## What the UI needs back

- `GET /quest/:slug/me` → `{ entry: { status, ticketCount, ticketsBySource, points, actionCount }, pendingActions, potentialTickets, rank, odds }`. The panel degrades gracefully if any field is missing.
- `GET /quest/:slug/leaderboard` → `{ top, me, totalParticipants, totalTickets }`. Rows are read as either `{ user: { _id, screenname, slug, photo } }` or those fields flattened onto the row; `me.pinned` drives the pinned row below the list.
- `stats.participantCount` / `totalTickets` / `totalActions` on the quest itself — the admin stat cards and list cards read these, so they need to be populated on list responses, not only on a single fetch.
- `GET /user?where={"_id":{"$in":[…]}}` — `results.winners` comes back as ids only, so the quest page resolves winner names **server-side** before render. A `screenname`/`photo` on the winner row would remove that call.
- `GET /quest/:slug/audit` → `{ tickets, ticketsHash, drawSeed, winners, derivation }`. The audit page folds `tickets` into a per-member holding count, so each ticket row needs a `userId`; a `screenname` or `slug` on it saves us a second lookup.
- `GET /questentry?where={"questId":"…"}` — used by the admin panel. A `user` object (or `screenname`) on the row would save a lookup here too.

## Still blocked on the backend

1. **Draft visibility** on `GET /quest` (above).
2. **Notifications.** Nothing emits `quest.closing.soon`,
   `quest.tickets.awarded` or `quest.winner.selected`.
3. ~~Lock / draw / settle have no UI.~~ **Done** — the quest page now drives
   verify, lock, draw and settle for admins. Two notes: we call `lock` with
   `{ force: true }` when `end` is still in the future and warn the admin first,
   and we hide `draw` until `results.winners` is empty, so the idempotent re-call
   is never triggered from the UI.
4. **Perk fulfilment.** `kind: 'perk'` awards carry no owner, expiry or blackout
   dates, so a won treehouse night can be claimed against a full calendar years
   later.
5. **Recurrence.** No `recurrence` field and no clone-into-next-window job, so a
   weekly quest has to be recreated by hand each week.
